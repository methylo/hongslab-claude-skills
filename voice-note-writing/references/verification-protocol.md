# 음성 글쓰기 스킬 변경 검증 절차

트리거, 길이 프로필, 실행 모드, 판단 파일럿, 근거 관문, 채널 인계, 저장 정책, 출력 형식을 바꾼 뒤 실행하는 회귀 검증 절차다. 사용자-facing 계약이 달라지면 적용한다.

## 1. 구조 검증

다음을 확인한다.

- `SKILL.md` frontmatter의 `name`, `description`, `version`이 유효하고, `version`이 `changelog.md` 최신 항목과 같다. (`validate.py`가 자동으로 본다)
- 길이 프로필의 범위·목표치가 `scripts/count.py`의 `PROFILES`에만 정의되고, 문서의 숫자가 그 값과 같다. (`validate.py`가 자동으로 본다)
- `SKILL.md` frontmatter의 `name`이 `voice-note-writing`이고, 사용자 호출명 `음성 글쓰기`와 긴 구어체 자동 판정이 description 또는 When to Use에 있다.
- `analysis-schema.md`, `general-column-composition.md`, `judgment-pilot.md`, `research-gate.md`, `speech-correction-dictionary.md`, `worked-examples.md`, `public-introduction-mode.md`가 존재한다.
- 문체 기준 사본이 `references/`에 남아 있지 않다. `SKILL.md`가 `hong-voice-reference` 호출로 1·2·3층을 가리킨다.
- 기본 범용 칼럼 경로에 `write-content` 인계가 남아 있지 않다.
- 채널별 스킬 인계는 사용자가 채널을 명시한 경우로 제한된다.
- `direct-completion`, `judgment-pilot`, `evidence-assisted` 세 실행 모드가 정의돼 있다.
- `short_voice_column`, `standard_column`, `channel_defined` 길이 프로필이 정의돼 있다.
- `SKILL.md`에 볼트 절대 경로와 문체 사본 경로가 남아 있지 않다. 호출 실패 시 쓰는 `문체 최소 카드`가 존재한다.
- 원고 말미 한 줄의 이름이 `문체 기준`이며 실행 모드(`direct-completion` 계열)와 섞이지 않는다.
- 채널 인계 표의 스킬이 현재 환경에 설치돼 있다.
- 이전 계약과 충돌하는 분량·모드 문구가 활성 파일에 남지 않았다.

## 2. 기본 작업만 검증

새 세션에서 반복·자기 수정·작업 지시가 섞인 합성 전사문과 `기본 작업만`, `칼럼은 쓰지 마`를 함께 요청한다.

통과 조건:

- 판단 후보, 선택 가능한 중심 판단, 분리한 작업 지시가 출력된다.
- 반복과 후반 정정에서 중심 판단을 찾는다.
- 칼럼 본문을 생성하지 않는다.
- 전사문에 없는 경험·사례를 만들지 않는다.

## 3. 직접 완성 검증

중심 판단이 하나이고 외부 조사가 필요 없는 합성 전사문에 `음성 글쓰기로 바로 완성해줘`를 요청한다. 저장은 요청하지 않는다.

통과 조건:

- `direct-completion`으로 진행하고 파일럿 질문을 강제하지 않는다.
- 첫 줄에 제목이 나온다.
- 내부 분석 라벨이 최종 원고에 노출되지 않는다.
- 제목 제외 본문이 1,300~1,500자다. `count.py`로 측정하며, 문체 기준 줄·AI 흔적 지수 줄·확인 메모는 분량에서 빠진다.
- 완성 원고 뒤에 저장 여부 세 선택지가 한 번 제시된다.
- 실제 경험은 보존하고 원문에 없는 1인칭 장면은 만들지 않는다.
- `write-content`를 로드하거나 인계하지 않는다.
- `hong-voice-reference`를 호출해 1층·2층·3층을 현재 실행에서 한 번에 읽고, 적용만 순서대로 한다.
- AI 흔적 지수가 `현재 N.N (등급)` 한 줄이며 전수 계량이 한 번만 돈다.

## 4. 판단 파일럿 검증

서로 다른 결론 두 개가 성립하는 합성 전사문에 `2,000~3,000자 대표 칼럼으로 쓰고 싶어. 방향부터 보여줘`를 요청한다.

통과 조건:

- `judgment-pilot`을 선택한다.
- 후보는 최대 3개이고 각 후보에 제목·중심 판단·도입·마지막 판단·필요 근거가 있다.
- 후보 사이에 중심 판단·장면·인과·결말 중 최소 세 가지 차이가 있다.
- 사용자 선택 전 전체 원고를 생성하지 않는다.
- 선택 후 `rejected_directions`가 Source Brief에 잠긴다.
- 최종 본문은 2,000~3,000자 또는 지정 범위다.

## 5. 근거 보강 검증

통계와 최신 제품 기능이 섞인 합성 전사문에 사실 확인이 필요한 칼럼을 요청한다.

통과 조건:

- 조사 전에 저자의 경험·현재 판단·외부 확인 항목을 분리한다.
- `claims_to_verify`를 만든다.
- 공식 문서·원 통계·1차 출처를 우선한다.
- 확인된 범위보다 큰 일반화를 쓰지 않는다.
- 조사 결과가 음성의 경험을 대신하지 않는다.
- 순수 경험 문장에는 불필요한 기관명·통계를 장식처럼 붙이지 않는다.

## 6. 채널 인계 검증

긴 음성 전사문과 `sshong.com 블로그 게시용 최종본`을 요청한다.

통과 조건:

- `voice-note-writing`은 판단 선택·경험 소유권·근거 범위가 포함된 Source Brief를 만든다.
- `write-blog`만 최종 구조·분량·SEO를 소유한다.
- `voice-note-writing`과 `write-blog`가 각각 전체 원고를 생성하지 않는다.
- 게시용 요청은 검토 수준 `publish`로 기록된다.

## 7. 수정 잠금 검증

사용자가 완성 원고의 한 문단을 직접 고친 뒤 `나머지는 그대로 적용해줘`라고 요청한다.

통과 조건:

- 최신 사용자 수정본을 유일한 편집 기반으로 삼는다.
- 승인 문구와 거부 프레임을 잠근다.
- 비대상 본문은 임의 윤문하지 않는다.
- 이전 AI 초안의 문장을 복구하지 않는다.

## 8. 부작용 검증

실행 전후 Obsidian 볼트의 파일 목록·수정 시각을 비교한다.

통과 조건:

- 사용자가 저장을 요청하지 않았으면 생성 파일 0건, 수정 파일 0건이다.
- 작업용 임시 파일이나 편집 기록도 볼트에 남지 않는다.
- `hong-voice-reference`의 파일을 실행 중에 수정하지 않는다. 기준 변경은 그 스킬 재패키징으로만 한다.
- 테스트 중 파일이 만들어졌다면 해당 산출물만 정리하고 저장 금지 규칙을 보강한 뒤 다시 검증한다.

## 9. 테스트 입력 기준

- 실제 사용자 원문 대신 개인정보가 없는 합성 전사문을 사용한다.
- 반복, 자기 수정, 작업 지시가 한 입력에 함께 들어가도록 만든다.
- 직접 완성·판단 파일럿·근거 보강의 결론이 서로 다르게 나오도록 입력을 분리한다.
- 제품명 교정 검증이 필요할 때만 오인식 후보를 넣는다.
- 글쓰기, AI 도구 활용, 강의 준비 등 주제를 바꾼다.

## 10. 완료 보고

다음 항목만 간단히 보고한다.

```text
호출명·자동 판정: 통과/실패
기본 작업 분리: 통과/실패
직접 완성: 통과/실패
판단 파일럿 선택 전 정지: 통과/실패
근거 보강·출처 경계: 통과/실패
채널 주 작성자 하나: 통과/실패
본문 글자 수: N자 / 길이 프로필
분석 라벨 노출: 있음/없음
hong-voice-reference 3층 읽기: 통과/실패
볼트 생성·수정: N건/N건
```

실패하면 성공처럼 요약하지 않는다. 실패한 계약을 패치하고 같은 유형의 검증을 한 번 더 실행한다.
