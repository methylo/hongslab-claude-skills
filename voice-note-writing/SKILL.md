# 음성 글쓰기 (voice-note-writing)

## Overview

주제·문장 구조 없이 이어진 음성 전사문에서 글쓴이의 경험과 중심 판단을 찾고, 필요한 경우 여러 글 방향을 짧게 시험한 뒤 범용 칼럼 또는 지정 채널 원고까지 이어지는 **음성 우선 글쓰기 워크플로우**다. 음성 인식(STT) 자체보다, 전사된 말에서 반복·자기 수정·말실수·편집 요청을 분리하고 글쓴이가 실제로 말하려던 판단을 끝까지 보존하는 데 집중한다.

사용자에게는 이 스킬을 **음성 글쓰기**라고 부른다. 사용자가 정확한 호출명을 쓰지 않아도, 긴 구어체 메시지에 반복·자기 수정·작업 지시가 섞여 있고 이를 글로 만들려는 요청이면 음성 입력으로 판정한다.

기본 실행은 다른 범용 글쓰기 스킬에 넘기지 않는다. 원문 잠금부터 분석, 실행 모드 판정, 필요한 근거 확인, 구조 설계, 초안, 리라이팅, 원문 역점검까지 이 스킬 안에서 수행해 **제목과 문단을 갖춘 완성된 글**을 만든다. 중심 판단이 분명하고 조사가 필요 없으면 바로 완성하고, 방향이 갈리거나 긴 대표 원고이면 `판단 파일럿`, 외부 사실이 필요하면 `근거 보강`을 먼저 거친다. 기본 분량은 제목 제외 1,300~1,500자이며, 사용자가 2,000~3,000자 칼럼이나 다른 분량을 지정하면 해당 길이 프로필을 따른다.

이 스킬의 기본 결과는 전사 요약, 메모 정리, 주제 후보 목록이 아니다. 사용자가 "방금 말한 걸 글로 써줘"라고 하면 분석 결과를 설명하는 데 머물지 않고 한 편의 공개 가능한 원고까지 완성한다.

## When to Use

다음 신호가 하나라도 있으면 사용한다.

- "음성 글쓰기로 작성해줘."
- "방금 음성으로 말한 걸 글로 써줘."
- "생각나는 대로 말할 테니 칼럼으로 정리해줘."
- "주저리주저리 말했는데 내가 무슨 말을 하려는지 찾아줘."
- "주제는 없는데 이 이야기에서 글감을 찾아줘."
- 문장 경계가 불분명한 긴 구어체 전사문이 입력됨
- 같은 생각이 다른 말로 반복되고, 결론이 발화 후반에 등장함
- 본문 소재와 "사례를 넣어줘", "더 짧게 써줘" 같은 작업 지시가 섞여 있음
- 제품명·고유명사·전문 용어의 음성 인식 오류가 의심됨

### 진입 후 되돌리는 경우

작업을 시작한 뒤에 다음이 확인되면 계속하지 않고 사용자에게 한 줄로 알린 뒤 멈춘다.

- 입력이 전사문이 아니라 이미 문어체로 완성된 글이다 → 문체 변환은 `edit-hongstyle`, AI 흔적 제거는 `edit-deai`, 부분 수정은 `edit-quick`
- 사용자가 원하는 결과가 완성 원고가 아니라 요약이나 발언자별 정리다

제외 대상 전체 목록은 frontmatter의 description에 있다. 여기서 다시 나열하지 않는다.

## Default Contract

별도 지시가 없으면 다음 계약으로 실행한다.

| 항목 | 기본값 |
|---|---|
| 입력 | 음성에서 전사된 비정형 한국어 텍스트 또는 같은 특징을 가진 긴 구어체 메시지 |
| 전체 작업 | 원문 보존 → 발화 분해 → 판단 후보·명확도 판정 → 직접 완성/판단 파일럿/근거 보강 선택 → 구조 설계 → 초안 → 리라이팅 → 원문 역점검 |
| 결과 유형 | 범용 칼럼 또는 지정 채널 원고를 위한 잠긴 Source Brief |
| 기본 분량 | 제목 제외 본문 1,300~1,500자 |
| 표준 장문 | 사용자가 요청하거나 대표 칼럼으로 판정되면 2,000~3,000자 또는 지정 범위 |
| 작성 방식 | 채널 미지정 범용 글은 다른 범용 글쓰기 스킬에 인계하지 않고 이 스킬 안에서 완성 |
| 실행 모드 | 중심이 분명하면 `direct-completion`; 방향이 갈리면 `judgment-pilot`; 외부 사실이 필요하면 `evidence-assisted` |
| 문체 | `hong-voice-reference` 스킬을 호출해 1층·2층·3층을 실행 시점에 읽어 적용 |
| 기본 출력 | 직접 완성 모드는 제목+완성 원고, 판단 파일럿은 방향 후보에서 정지 |
| 저장 | 사용자가 명시적으로 요청하지 않으면 대화창에만 출력하고 파일·Obsidian 노트를 만들지 않음 |
| 분석 노출 | 사용자가 요청했거나 선택이 필요한 판단 파일럿일 때만 |
| 확인 질문 | 서로 양립하지 않는 중심 판단이 있고 파일럿만으로 선택하기 어렵거나, 핵심 사실·고유명사 확인이 필요할 때만 |

사용자가 "기본 작업만", "주제만 추출", "글쓰기 재료로만 정리"라고 하면 Source Brief까지만 제공하고 칼럼을 쓰지 않는다. 사용자가 `한 번에`, `바로 완성`, `알아서 끝까지`라고 해도 확인되지 않은 사실을 만들지는 않지만, 중심 판단이 하나이면 판단 파일럿을 생략한다.

## Voice-First Contract

이 스킬은 음성을 문어체로 정리하는 도구가 아니라 저자의 소유 재료를 확보하고 그 뒤의 선택·조사·집필·검토를 운영하는 방식이다.

1. **음성 우선, 음성 강제 금지** — 경험·관점·판단이 중심이면 음성을 기본 입력으로 추천한다. 순수 리서치 보고서·완성 초안 교정·책 전체 집필에는 음성만을 강제하지 않는다.
2. **판단 먼저, 조사 나중** — 외부 자료가 필요해도 먼저 저자의 판단 후보와 경험 경계를 잠근다. 조사가 저자의 관점을 대신하지 않게 한다.
3. **짧은 파일럿, 한 명의 최종 작성자** — 방향 비교가 필요하면 제목·도입·마무리만 시험한다. 전체 원고는 주 작성자 하나가 쓴다.
4. **필요한 조사만** — 통계·최신 제품 사실·외부 일반화가 있을 때만 근거 보강을 연다. 경험형 글에 자료를 장식처럼 붙이지 않는다.
5. **검토 깊이 최소화** — 일반 원고는 Step 10 역점검으로 끝낸다. 게시용·기고문일 때만 `hong-voice-reference` 3층을 한 번 더 통과시킨다. 모든 음성 글에 다중 검토를 강제하지 않는다.

## 문체 기준 로드 (외부 정본 호출)

범용 칼럼의 구조와 작성 절차는 이 스킬이 소유한다. **문체·표현·AI 흔적 기준은 이 스킬이 소유하지 않는다.** `hong-voice-reference` 스킬이 정본이다.

1. `Skill` 도구로 `hong-voice-reference`를 호출한다.
2. 반환된 `Base directory`를 BASE로 두고 필요한 층만 읽는다. **1층·2층·3층은 Step 9 진입 시 한 번에 읽는다.** 층 순서 규칙은 적용 순서이지 읽기 순서가 아니다. 세 번 나눠 읽으면 왕복만 세 배가 된다.

| 파일 | 역할 | 적용 층 | 읽는 시점 |
|---|---|---|---|
| `{BASE}/references/01-voice.md` | 시선, 논리 흐름, 어조, 문장 리듬, 마무리 방식 | 1층 | Step 8 초안 전, Step 9 |
| `{BASE}/references/02-glossary.md` | 실제로 쓸 단어·문장 선택, 낯선 표현 교체 | 2층 | Step 9 |
| `{BASE}/references/03-anti-traces.md` | 과장, 빈 완곡어, 상투적 연결, 챗봇식 마무리 제거 | 3층 | Step 9, Step 10 직전 |
| `{BASE}/references/04-examples.md` | 승인된 실제 문단 | 공통 | 문체 판정이 갈릴 때만 |
| `{BASE}/references/05-corrections.md` | 교정 이력 | 공통 | 같은 표현을 두 번 이상 고쳤을 때만 |

- 최종 원고를 쓰는 실행마다 호출한다. 과거 세션에서 읽은 내용이나 다른 글쓰기 스킬의 요약 규칙으로 대체하지 않는다.
- **적용** 순서를 지킨다. 시선·구조(1층)가 정리되기 전에 단어(2층)나 흔적(3층)부터 만지면 같은 문장을 두 번 고치게 된다. 읽기는 한 번에 하고 손대는 순서만 지킨다.
- 같은 대화에서 이미 읽은 파일은 다시 읽지 않는다.
- 호출이 실패하면 이 문서 하단 `문체 최소 카드`로 진행한다.

### 문체 기준 표기 (필수)

최종 원고 말미에 아래 한 줄을 **항상** 붙인다. 성공·실패 모두 적는다. 이 줄이 없으면 문체 기준을 로드하지 않은 것이다. `direct-completion`·`judgment-pilot`·`evidence-assisted`를 가리키는 `실행 모드`와 다른 항목이므로 원고에 모드명을 적지 않는다.

```text
문체 기준: hong-voice-reference (1층·2층·3층 적용)
문체 기준: 폴백 최소 카드 (hong-voice-reference 호출 실패)
AI 흔적 지수: 현재 N.N (등급)
```

본문에서 설명하지 않는다. 한 줄로 끝낸다.

**갱신 방법**: 기준을 고치려면 `hong-voice-reference` 스킬을 다시 패키징한다. 이 스킬은 문체 기준 파일을 갖지 않으므로 갱신 대상이 아니다.

## Source Priority

1. 원본 전사문과 현재 요청
2. 사용자가 직접 밝힌 경험·판단·표현
3. 같은 대화에서 확인된 제품명·프로젝트명·고유명사
4. 프로젝트별 용어사전
5. 이 스킬의 처리 순서
6. 채널이 명시된 경우의 채널 글쓰기 스킬
7. `hong-voice-reference` 1층·2층·3층

확인되지 않은 경험, 수치, 사례, 발화는 만들지 않는다. 제3자의 경험을 사용자의 1인칭 경험으로 바꾸지 않는다.

## Workflow

경로는 두 갈래다. 중심 판단이 하나로 분명하면 **통합 관문**으로 확인을 1회로 줄이고, 방향이 갈리면 파일럿 경로로 단계마다 멈춘다.

```text
공통    Step 1 원문 잠금 → 2 발화 분해 → 3 반복 묶기 → 4 판단 후보 잠금
        ↓
        Step 4.5 통합 관문  ── 조건 충족 → 확인 1회 → Step 6으로
        ↓ (조건 미충족)
파일럿   Step 5 주제 수 → 7.5 실행 모드·길이·근거
        ↓
공통    Step 6 전사 교정 → 7 Source Brief → 8 초안 → 9 문체 3층 → 10 역점검
```


### Step 1. 원문 잠금

원본 전사문을 그대로 보존하고 별도 작업본에서 분석한다. 맞춤법과 반복을 먼저 고치지 않는다. 말실수, 되돌아간 표현, 반복 횟수도 중심 생각을 찾는 단서다.

작업본은 파일이 아니라 이번 실행의 작업 맥락 안에 둔다. 저장 요청이 없으면 원문·작업본 어느 쪽도 파일로 만들지 않는다. Step 10의 분량 측정용 임시 파일만 예외이며 측정 직후 지운다.

완료 기준: 원문과 작업본이 구분되고, 원문에서 고친 부분을 작업본에서 추적할 수 있다.

### Step 2. 발화 단위 분해

`references/analysis-schema.md`를 읽고 각 의미 단위를 다음 중 하나 이상으로 분류한다.

| 분류 | 내용 |
|---|---|
| 경험 | 실제로 했거나 겪은 일 |
| 관찰 | 사람·상황·도구를 보고 느낀 점 |
| 판단 | 현재 중요하다고 보는 내용 |
| 사례 | 판단을 보여주는 장면·예시 |
| 작업 지시 | 분량·사례·톤·형식에 관한 요청 |
| 전사 불확실성 | 오인식 가능성이 있는 제품명·고유명사·수치·전문 용어 |
| 후속 글감 | 중심 글에는 들어가지 않지만 별도 글이 될 내용 |
| 군더더기 | 삭제해도 의미·온도·강조가 유지되는 부분 |

`analysis-schema.md`의 코드 8종(E·O·J·C·I·U·F·X)과 같은 분류다. 한 문장에 내용과 작업 지시가 함께 있으면 둘로 나눈다.

작업 지시 가운데 원문 재료로 충족할 수 없는 것이 있으면(예: 사례를 더 넣어 달라고 했는데 원문에 사례가 하나뿐) 지시를 채우려고 사례를 만들지 않는다. 있는 재료로만 쓰고, 무엇을 채우지 못했는지 원고 뒤에 한 줄로 알린다.

분해가 처음이거나 판단이 서지 않으면 `references/worked-examples.md`를 읽는다. 분해 예시 2건과 실패 예시 3건(첫 문장을 주제로 고정 / 작업 지시를 본문에 삽입 / 일반론으로 과도하게 정리)이 있다.

완료 기준: 주요 의미 단위마다 분류가 있고, 작업 지시가 본문 소재와 분리되며, 불확실한 전사가 별도 표시되어 있다.

### Step 3. 반복 묶기

같은 뜻을 다른 말로 되풀이한 표현을 한 묶음으로 모은다. 반복을 곧바로 군더더기로 지우지 않는다. 반복 횟수, 발화 후반의 정정, "결국", "내가 말하려는 것은" 뒤의 문장을 함께 본다.

각 반복 묶음에서 다음을 남긴다.

1. 사용자가 가장 직접적으로 말한 표현
2. 반복이 가리키는 공통 생각
3. 글에서 보존할 온도나 망설임
4. 삭제해도 의미가 바뀌지 않는 군더더기

완료 기준: 반복된 생각이 하나의 판단 문장으로 수렴하면서도 사용자 표현 하나 이상이 남아 있다.

### Step 4. 판단 후보·중심 의도·명확도 잠금

`references/analysis-schema.md` 3항의 절차를 따른다. 반복 묶음과 후반 정정에서 가능한 중심 판단을 최대 3개까지 적고, 각 후보가 원문 근거를 갖는지·다른 결론을 요구하는지·글 전체를 지탱하는지·작업 지시를 판단으로 잘못 읽지 않았는지 확인한다. 그다음 가장 강한 후보로 중심 의도 한 문장과 독자·글의 역할 한 줄을 내부적으로 완성한다.

독자가 명시되지 않았고 내용만으로 특정하기 어려우면 일반 AI 활용 입문자·실무자를 기본 독자로 둔다. 특정 직업·연령·조직을 임의로 만들지 않는다.

완료 기준:

- 중심 의도 한 문장에 핵심 내용이 들어간다.
- 들어가지 않는 내용은 `보조 사례 / 후속 글감 / 작업 지시`로 이동한다.
- 판단 명확도를 `high / medium / low` 중 하나로 기록한다.

#### 시간순 변화 글의 순서·관계 잠금

음성 원문이 도구·방법·작업 방식의 변화를 시간순으로 말하면 중심 의도와 별도로 두 항목을 잠근다.

1. **실제 순서** — 사용자가 직접 정정한 순서를 그대로 유지한다. 익숙한 분류나 제품 출시 순서로 재배열하지 않는다.
2. **단계 사이의 관계** — `교체`, `병행`, `축적`, `통합` 중 무엇인지 구분한다. 새 도구를 쓰기 시작했다는 이유만으로 앞의 방식을 버렸다고 쓰지 않는다.

마지막 단계가 이전 경험을 한곳에서 활용하는 단계라면 각 요소를 기능 목록으로 다시 나열하는 데서 멈추지 않는다. 앞에서 익힌 지시 방식, 반복 기준, 파일 작업, 지식 저장·연결 방식이 마지막 도구 안에서 **하나의 작업 흐름으로 이어진다**는 현재 판단을 중심에 둔다.

사용자가 순서나 관계를 정정하면 해당 문단만 기계적으로 바꾸지 않는다. 제목·도입·앞뒤 전환·마무리에 남은 `대체`, `이동`, `갈아탐` 프레임을 다시 확인한다.

완료 기준: 사용자 확정 순서가 제목부터 마지막 문단까지 어긋나지 않고, 누적·통합 경험이 제품 교체 서사로 바뀌지 않는다.

### Step 4.5. 통합 관문 (조건 충족 시 Step 5·7.5를 대신한다)

Step 4를 마친 시점에 아래 네 가지가 모두 맞으면 Step 5와 Step 7.5를 따로 돌리지 않고 **확인 1회로 묶는다.**

```text
1) 중심 판단이 하나이고 명확도가 high
2) 서로 다른 결론을 요구하는 후보가 없다
3) 통계·최신 제품 사실·외부 일반화를 새로 확인할 필요가 없다
4) 사용자가 한 번에 완성을 요청했거나 기본 1,300~1,500자 범용 칼럼이다
```

네 가지가 곧 `direct-completion` 진입 조건이다. 이 경우 아래 한 블록만 출력한다.

사용자가 `한 번에`, `바로 완성`, `알아서 끝까지`를 요청했으면 **블록을 출력하고 답을 기다리지 않고 Step 6으로 간다.** 그 요청이 없었을 때만 한 번 멈춰 이의를 받는다. 기다릴지 말지를 매번 다시 판단하지 않는다.

```text
[잠금]
중심 판단   (한 문장)
독자        (한 줄)
주제 수     1개 — 보조 논점: (있으면 나열)
실행 모드   direct-completion
길이        short_voice_column 1,300~1,500자 (목표 1,400)
조사        불필요
제외        (후속 글감 / 작업 지시로 옮긴 것)
```

하나라도 어긋나면 이 관문을 쓰지 않고 Step 5와 Step 7.5를 순서대로 돌린다. 판단 파일럿이 필요한 글에서 관문을 묶으면 방향이 갈린 채 전체를 쓰게 된다.

완료 기준: 잠금 블록 하나로 중심 판단·주제 수·실행 모드·길이·조사 여부가 모두 확정됐다.

### Step 5. 주제 수 판정 (파일럿 경로)

> Step 4.5 통합 관문을 통과했으면 이 단계를 건너뛴다.


- 중심 판단이 하나면 확인 없이 다음 단계로 간다.
- 관련된 판단 여러 개가 하나의 인과를 이루면 한 글의 보조 논점으로 둔다.
- 서로 다른 결론을 요구하면 `가장 강한 주제 / 별도 글 / 메모`로 나눈다.
- 두 후보의 우열을 정할 근거가 없고 결과가 크게 달라질 때만 최대 3개 후보로 사용자에게 선택을 묻는다. 이때 `선택지를 묻는 방법` 절을 따른다.

완료 기준: 이번 원고가 증명할 중심 판단이 하나다.

### Step 6. 전사 교정

`references/speech-correction-dictionary.md`를 읽는다.

- 같은 대화와 프로젝트 문맥으로 교정이 분명한 표현만 고친다.
- 제품명·인명·기관명·수치처럼 교정에 따라 사실이 달라지면 추측하지 않는다.
- 불확실한 표현이 중심 논지와 무관하면 자연스럽게 우회한다.
- 중심 논지에 필요하면 `확인이 필요한 표현`으로 한 번만 묻는다.
- 한 번 나타난 오인식을 공용 규칙으로 승격하지 않는다.

완료 기준: 본문에 사실을 바꿀 수 있는 임의 교정이 없다.

### Step 7. Source Brief 작성

`references/analysis-schema.md` 5항의 템플릿으로 내부 작업물을 만든다. 필수 슬롯은 다음과 같다.

추출한 주제 · 판단 후보와 명확도 · 선택된 중심 판단과 폐기한 방향 · 실제 문제·관찰 · 보존할 경험과 사용자 표현 · 사용할 사례 · 글쓰기 지시 · 확인이 필요한 표현 · 확인할 주장과 출처 경계 · 길이 프로필과 검토 수준 · 제외하거나 후속으로 돌릴 내용 · 권장 글 유형·채널·최종 주 작성자

검토 수준은 두 값 중 하나다. `basic`은 Step 10 역점검으로 끝내고, `publish`는 게시용·기고문일 때 문체 기준 3층을 한 번 더 통과시킨다.

`direct-completion`에서는 위 필수 슬롯만 채운다. `analysis-schema.md` 5항의 YAML 전체(48줄)를 빈 값으로 채워 완성하지 않는다. 파일럿·근거 보강 경로에서 `judgment.candidates`, `research.*`가 실제로 쓰일 때 그 블록만 추가한다.

Source Brief는 기본적으로 내부 작업물이다. 사용자가 "어떻게 분석했는지 보여줘"라고 했을 때만 노출한다.

완료 기준: 다음 작성 단계가 원본 전사문을 다시 해석하지 않아도 판단 후보·사실 경계·보존 표현을 알 수 있다.

### Step 7.5. 실행 모드·길이·근거 관문 (파일럿 경로)

> Step 4.5 통합 관문을 통과했으면 이 단계를 건너뛴다. 아래는 관문에서 걸러진 글에만 적용한다.

`references/judgment-pilot.md`와 `references/research-gate.md`를 필요한 분기에서만 읽는다.

#### A. 직접 완성 `direct-completion`

Step 4.5의 네 조건을 그대로 쓴다. 조건 문구는 Step 4.5 한 곳에만 두며 여기서 다시 나열하지 않는다. 네 가지가 모두 맞으면 파일럿 없이 Step 8로 간다. Step 4.5에서 한 항목만 어긋나 관문을 쓰지 못했더라도, 이 단계에서 그 항목이 해소되면 직접 완성으로 돌아올 수 있다.

#### B. 판단 파일럿 `judgment-pilot`

다음 중 하나면 전체 원고 전에 방향 후보 최대 3개를 만든다.

- 서로 다른 중심 판단이 두 개 이상 성립한다.
- 2,000~3,000자 대표 칼럼·블로그·기고문이다.
- 사용자가 방향·앵글·구조를 먼저 보고 싶어 한다.

각 후보는 `제목 / 중심 판단 / 도입 3~4문장 / 마지막 판단 1~2문장 / 필요한 경험·근거`의 다섯 항목만 보여준다. 후보마다 장점·주의점·평가표를 붙이지 않는다. 사용자가 비교·추천도 요청했으면 모든 후보 뒤에 추천 번호와 이유 1~2문장만 별도로 제시할 수 있다. **사용자 선택 전에는 전체 원고를 쓰지 않는다.** 사용자가 `바로 완성`을 명시했고 중심 판단이 하나이면 긴 글이라는 이유만으로 파일럿을 강제하지 않는다.

#### C. 근거 보강 `evidence-assisted`

선택된 판단에 다음이 포함되면 조사 항목만 분리한다.

- 통계·수치·연도·기관 주장
- 최신 제품 기능·가격·접근 범위
- 제3자 사례나 일반화
- 독자가 따라 할 절차의 현재 유효성

먼저 `claims_to_verify`를 잠그고 필요한 1차·공식 출처만 확인한다. 순수 경험형 글에는 조사 문단을 장식처럼 추가하지 않는다.

이 스킬은 과거 글을 스스로 찾지 않는다. 사용자가 겹치지 않게 할 글을 직접 붙여 주면 그 글의 중심 주장·도입 장면·대표 표현을 새 글에서 다시 쓰지 않는다. 붙여 준 글이 없으면 중복 확인을 하지 않으며, 추측으로 제외 목록을 만들지 않는다.

#### 길이 프로필

- `short_voice_column`: 제목 제외 1,300~1,500자
- `standard_column`: 제목 제외 2,000~3,000자 또는 사용자가 지정한 범위
- `channel_defined`: 지정 채널 스킬의 분량 계약

완료 기준: 실행 모드 하나, 길이 프로필 하나, 조사 필요 여부, 최종 주 작성자가 잠겼다.

### Step 8. 범용 칼럼 구조 설계와 초안 작성

채널 지시가 없으면 `references/general-column-composition.md`를 읽고 선택된 길이 프로필에 맞춰 이 스킬 안에서 구조를 설계하고 초안을 작성한다. `write-content`를 후단 엔진으로 로드하거나 인계하지 않는다.

```text
비정형 음성·긴 구어체 입력
→ 원문 잠금과 발화 분석
→ 판단 후보·명확도·Source Brief
→ 직접 완성 또는 판단 파일럿
→ 필요한 근거 확인
→ 길이 프로필에 맞는 범용 칼럼 구조
→ 주 작성자 한 명의 전체 초안
→ 문체 기준 3층 적용
→ 원문·선택 판단·근거 역점검
→ 제목 + 최종 원고
```

#### 분량 예산

초안을 쓰기 전에 문단 수를 먼저 잡는다. 다 쓴 뒤 모자란 만큼 덧붙이는 방식은 원문에 없는 장면을 불러들인다.

목표치와 범위는 `scripts/count.py`의 `PROFILES`가 단일 기준이다. 아래 표는 그 값을 옮긴 것이므로, 숫자를 바꾸려면 스크립트를 먼저 고친다.

| 프로필 | 목표치 (`target`) | 범위 | 문단 수 |
|---|---|---|---|
| `short_voice_column` | 1,400자 | 1,300~1,500 | 9~12문단 |
| `standard_column` | 2,400자 | 2,000~3,000 | 14~18문단 |

문단 수를 먼저 정한 뒤 **문단당 목표 글자 수 = 목표치 ÷ 문단 수**를 계산한다. 10문단이면 140자, 12문단이면 117자다. 이 값을 적어두고 시작한다.

이 값은 승인 원문보다 낮은 쪽이다. `04-examples.md` 승인 원문 18개 문단의 실측은 중앙값 174자, 사분범위 87~244자다. 문단이 100자 아래로 내려가면 리듬이 짧은 것이 아니라 이유·결과·조건이 빠진 것이다. 판단 문장 세 개로 문단을 닫고 다음으로 넘어가는 패턴이 반복되면 초안 전체가 목표의 절반에서 끝난다.

문단 수만 잡고 쓰면 문단이 두세 문장에서 끊겨 1차 초안이 목표의 절반에서 멈춘다. 검증에서 두 번 재현된 회귀다. 다음 두 가지로 막는다.

1. 문단을 진행하면서 남은 예산을 확인한다. 전체가 목표의 절반에서 멈출 것 같으면 그 지점에서 이유·결과·조건 중 하나를 이어 붙인다. 문단마다 같은 글자 수를 채우라는 뜻이 아니다.
2. 1차 초안을 끝낸 즉시 `count.py`를 돌린다. Step 10까지 미루지 않는다. `verdict`가 `미달`이거나 `near_floor`가 `true`이면 문단을 새로 만들지 말고 짧은 문단부터 채운다. 채울 양은 `gap`이 아니라 **`to_target`**이다. `gap`은 하한까지의 거리라서 그만큼만 채우면 하한에 착지하고 같은 판정이 다시 나온다. `paragraphs.thin`이 보강할 문단 번호를 직접 알려주고, `thin_run`이 3 이상이면 전개가 빠진 구간이다. `paragraphs.median`을 승인 원문 중앙값 174자와 비교한다.

하한을 겨우 넘기는 원고를 목표로 삼지 않는다. `near_floor`는 범위 하위 25%에 있다는 신호이며 계약 위반이 아니다. 보강할 자리가 있는지 확인하고, 없으면 그대로 둔다. 남거나 모자라면 문단 수가 아니라 각 문단이 맡은 역할을 다시 본다.

문단당 목표 글자 수는 **총량 배분용 예산**이지 문단 규격이 아니다. `01-voice.md` §3-1은 문단을 일정한 문장 수·단어 수에 맞추지 말라고 규정한다. 한 문장짜리 문단과 긴 설명 문단이 섞여도 총량이 맞으면 예산을 지킨 것이다. 예산을 맞추려고 문단 길이를 균일하게 만들지 않는다.

분량이 모자랄 때 늘릴 수 있는 것은 넷뿐이다.

1. 이미 말한 판단이 왜 그렇게 되었는지의 전개
2. 원문에 있는 장면의 결과나 그 뒤의 행동
3. 확인된 외부 사실과 그 적용 범위
4. 이 판단이 적용되지 않는 조건

새 장면, 새 인물, 새 수치, 새 대화, 원문에 없는 감각 묘사로는 늘리지 않는다. 넷으로도 채우지 못하면 늘리는 대신 중심 판단이 좁은지 확인하고, 그래도 부족하면 재료 부족을 사용자에게 알린다.

구조는 고정 슬롯이 아니라 선택된 중심 판단을 가장 잘 드러내는 인과를 따른다. 원문에 실제 경험이나 엉뚱했던 기대가 있으면 설명보다 앞세우고, 없으면 1인칭 장면을 만들지 않는다. 모든 문단을 같은 길이로 맞추거나 도입·사례·결론을 기계적으로 채우지 않는다. 표준 장문은 문단을 늘리는 방식이 아니라 확인된 근거·반론·적용 조건 가운데 중심 판단에 필요한 층만 추가한다.

초안 완료 기준:

- 선택된 중심 판단이 제목 후보·도입·본문·마무리에 일관되게 반영되어 있다.
- 파일럿에서 폐기한 방향이 되살아나지 않았다.
- 음성의 작업 지시가 본문 주장으로 섞이지 않았다.
- 원문에 없는 1인칭 경험이나 사례가 추가되지 않았다.
- 분량을 채우려고 새 장면·인물·수치·대화·감각 묘사를 넣지 않았다.
- 외부 사실은 확인된 범위와 출처 경계를 벗어나지 않았다.
- 제목 제외 본문이 선택된 길이 프로필의 목표치 부근이다. 하한을 겨우 넘긴 상태가 아니다.

### Step 9. 문체 기준 3층 적용과 리라이팅

`hong-voice-reference`를 호출해(`문체 기준 로드` 절 참조) 세 층을 이번 실행에서 직접 읽고 순서대로 적용한다.

세 파일을 한 번에 읽은 뒤 아래 순서로 **적용**한다. 파일마다 읽기를 나누지 않는다.

1. `01-voice.md` — 시선, 논리 흐름, 어조, 문장 리듬을 조정한다.
2. `02-glossary.md` — 사용자에게 익숙하지 않은 표현을 걷어내고 실제 어휘에 맞춘다.
3. `03-anti-traces.md` — 과장, 빈 완곡어, 상투적 연결, 챗봇식 마무리를 문맥에 따라 정리한다.

문체 기준을 적용하면서 원문의 사실·경험·현재 판단을 바꾸지 않는다. 삭제한 표현의 의미가 필요하면 조건, 장면, 비교, 실제 행동 또는 판단 문장으로 바꾼다.

완료 기준:

- 세 층을 현재 실행에서 모두 읽었다.
- 최종 원고 말미에 문체 기준 한 줄과 AI 흔적 지수 한 줄(`현재 N.N (등급)`)을 붙였다. 전수 계량은 한 번만 한다.
- 표현 정리가 사용자의 경험과 판단을 일반론으로 바꾸지 않았다.
- 원고 **본문**에 문체 기준 설명이나 검사 보고가 섞이지 않았다. 본문 뒤 문체 기준 한 줄과 AI 흔적 지수 한 줄은 예외로 붙인다.

### Step 10. 최종 역점검

최종 원고를 원본 전사문과 다시 비교한다.

1. 사용자가 가장 많이 반복하거나 마지막에 정정한 생각이 남아 있는가
2. 파일럿에서 사용자가 선택한 판단이 제목·도입·본문·마무리에 유지되는가
3. 매끈한 설명을 위해 사용자의 판단을 일반론으로 바꾸지 않았는가
4. 실제 경험이 기능 설명이나 외부 자료로 대체되지 않았는가
5. 작업 지시가 본문 문장으로 들어가지 않았는가
6. 불확실한 전사를 사실처럼 확정하지 않았는가
7. 확인 대상 주장이 출처 범위보다 커지지 않았는가
8. 모든 문단이 같은 길이와 판단형 종결로 반듯하게 닫히지 않았는가
9. 제목 제외 본문이 선택된 길이 프로필 범위에 들어가는가

9번은 눈대중으로 판정하지 않는다. 원고를 임시 파일에 쓰고 다음을 실행해 숫자로 확인한다.

원고 쓰기·측정·삭제를 한 명령으로 처리한다. 세 번 왕복하지 않는다.

```bash
cat > /tmp/vnw_count.md <<'EOF'
<원고 본문>
EOF
python3 {SKILL_BASE}/scripts/count.py /tmp/vnw_count.md --profile short_voice_column; rm -f /tmp/vnw_count.md
```

`{SKILL_BASE}`는 이 스킬의 `Base directory`다. 작업 디렉터리가 스킬 폴더라는 보장이 없으므로 상대 경로로 부르지 않는다.

문체 기준 한 줄, AI 흔적 지수 한 줄, 확인 메모는 스크립트가 알아서 제외한다. 측정용 임시 파일에서 그 줄들을 직접 지울 필요는 없다.

`verdict`가 `초과`면 반복 설명부터 줄이고, `미달`이면 새 사례를 만들지 말고 `paragraphs.thin`이 가리키는 문단에서 경험·관찰·근거와 판단의 연결이 생략되었는지 확인한다. 보강량은 `to_target` 기준이다. `near_floor`가 `true`면 하한 근처라는 뜻이므로 보강할 자리만 확인하고, 없으면 그대로 내보낸다. 스크립트를 쓸 수 없는 환경이면 위 세 줄을 뺀 뒤 공백을 뺀 글자 수를 직접 세고, 센 값을 원고와 함께 알린다.

미달 항목이 있으면 해당 부분만 수정하고 문체 기준과 원문을 한 번 더 대조한다.

## Output Modes

### 기본 모드: 완성 원고 우선

```text
# 제목

본문
```

분석 리포트, 내부 분류표, AI 흔적 검사 과정·범주별 내역은 붙이지 않는다. 다만 `03-anti-traces.md` §11이 요구하는 지수 한 줄과 문체 기준 한 줄은 본문 뒤에 붙인다. 이 스킬의 원고는 전사문에서 새로 쓰는 글이므로 §11의 신규 생성 규칙을 따라 `AI 흔적 지수: 현재 N.N (등급)` 한 줄로만 적는다. 초안과 리라이팅본을 각각 채점해 두 값을 비교하지 않는다. 사용자가 `저장해줘`, `Obsidian에 넣어줘`, `파일로 만들어줘`처럼 저장을 명시하지 않으면 파일 도구를 호출하지 않고 대화창에만 원고를 출력한다.

`evidence-assisted`로 외부 사실을 확인한 경우에만 원고 뒤에 `확인 메모`를 붙인다. 본문 안에 넣지 않는다. 형식은 세 줄 이내로 고정한다.

```text
확인 메모
- 확인한 주장: 출처명 + 링크 + 확인일
- 확인하지 못한 주장: 처리 방식(체감 표현 유지 / 본문 제외 / 범위 축소)
```

조사가 없었던 실행에는 확인 메모를 붙이지 않는다. 저장 요청이 있으면 확인 메모는 저장 파일에 포함하지 않는다.

완성 원고를 낸 뒤에는 `저장하기 / 조금 고치기 / 이번에는 저장하지 않기` 세 선택지를 한 번 제시한다. 자동 저장은 하지 않는다. 사용자가 저장을 고르면 `references/modes-optional.md`의 저장 규칙을 읽고 경로를 묻는다. 이 스킬은 저장 위치를 알지 못하므로 기본 경로를 추측해 만들지 않는다.

## Verification Checklist

단계별 완료 기준은 각 Step에 있다. 여기서는 원고를 내보내기 직전에 확인할 항목만 둔다.

- [ ] 이번 글의 중심 판단이 하나다.
- [ ] 실행 모드 하나를 골랐고, 파일럿이면 사용자 선택 전 전체 원고를 만들지 않았다.
- [ ] 원문에 없는 경험·사례·장면·수치를 만들지 않았다.
- [ ] 불확실한 제품명·고유명사·수치를 임의 확정하지 않았다.
- [ ] 선택하지 않은 방향이 되살아나지 않았다.
- [ ] `hong-voice-reference`를 이번 실행에서 호출해 1층 → 2층 → 3층 순서로 적용했다.
- [ ] 최종 원고 말미에 문체 기준 한 줄과 AI 흔적 지수 한 줄(`현재 N.N (등급)`)을 붙였다.
- [ ] `count.py`로 분량을 확인했고 `verdict`가 `충족`이다. `near_floor`이면 보강 여부를 판단했다.
- [ ] 완성 원고 뒤에 저장 여부 세 선택지를 한 번 제시했다.
- [ ] 저장 요청이 없으면 파일·Obsidian 노트를 만들지 않았다.
- [ ] 최종 출력이 분석 보고서가 아니라 제목과 본문이다.
